# AI UI Proposal V2 architecture

## Phase 0 root cause audit (before implementation)

The reported Vietnamese request reached the V1 `/ui-proposals/generate` route as plain text. The route passed only five indexed path/symbol hints to `generate_ui_spec`; it neither classified a modification operation nor resolved a UI element. `OfflineDemoProvider.generate_ui_spec` always built a new root `Container` and generic card. Its original fallback was a `New request` form; the later keyword patch changed that to an isolated button card, but still discarded the surrounding UI. The Meta path likewise requested a full `StructuredUISpecV1` with no target identity or patch contract. The React workspace rendered only the returned new spec; it had no before baseline, target choices, or distinction between a source-backed target and a conceptual illustration. Session history stored whole specs but refinement asked the provider to regenerate the whole tree. Impact analysis sent only prose, omitting validated target references and patch details.

The selected bundled Python authentication repository does not contain ScopeGraph's own impact-analysis button. Its label cannot be grounded to that repository. A matching name in the user's request is not evidence of a source target. V2 must therefore report a conceptual target for that selection, or a source-backed candidate only when the selected indexed repository actually contains the element.

## API and execution flow

`POST /api/v1/repositories/{id}/ui-proposals/generate` retains the V1 request fields and adds `mode: "offline" | "live"`, optional `target_label`, and optional `selected_target_path` (a `path:line` candidate reference). The browser sends `mode` explicitly. The response adds `intent`, `patch`, `target_resolution`, `before_spec`, `preview_provenance`, and `change_summary` to the V1 `spec` and `generation` fields. `GET /api/v1/repositories/{id}/ui-proposals/status` reports offline/live availability without credentials. Private repository status and generation both require an owner session; the bundled sample is allowed only in its expected workspace and remains offline only.

The server classifies the instruction into one of seven operations. The offline classifier recognizes a bounded vocabulary; it reports high uncertainty when the target is absent. A modification without a target fails with 422 rather than creating a generic form. A named target is searched only within indexed UI files under the selected repository root. Literal JSX text/accessible labels and statically resolvable `t('key')` localization references can produce candidates. Results contain a repository-relative path, element hint, source line, excerpt and match reason. The resolver does not execute code or read unindexed files. Multiple candidates return 409 with choices; the caller must select a `path:line` reference. No match is marked conceptual.

`UIPatchV2` is strict and versioned. `UIChangesV2` permits only enum colors (`lime`, `red`, `dark_red`, `ink`), shape (`soft`, `square`), fixed left icons, bounded desktop columns, an inert validated component, removal, or an explicit preserve-size constraint. Arbitrary CSS, HTML, JavaScript, URLs and event handlers are absent from the schema. The patch function deep-copies `StructuredUISpecV1`, locates exactly one node, changes only supported properties, and revalidates the whole tree. Existing text, interaction enum and other nodes remain intact. Add/remove operations work on the structured proposal, not repository source. The renderer uses fixed React components and Tailwind classes.

For a prior proposal version, `before_spec` is that version and `preview_provenance=proposal_version`. For an initial style edit without a prior spec, the server creates a one-button conceptual baseline and returns `conceptual_approximation`. This is **not** a screenshot or exact reconstruction of repository UI. A new page has `new_proposal` provenance and no before screen. The workspace renders Before/After side by side when a baseline exists, with desktop/mobile toggles, target evidence, version selection, return-to-previous action and exported JSON. Proposal history is per browser session; it is not cross-device storage. Prior reports are marked stale after refinement.

## Live mode and security

Live UI inference is opt-in per request and server-side (`UI_PROPOSAL_LIVE_ENABLED=true`). It is available only in development for an authenticated owner of the selected repository with `META_AI_PROVIDER=meta_model_api`, a nonempty `META_AI_API_KEY`, and an approved HTTPS Meta endpoint. It uses the existing `MetaAIHttpProvider` and `StageProviderRouter` UI generation stage. New-page requests ask for `StructuredUISpecV1`; edits ask for `UIPatchV2` and compare the returned target with the selected target before applying it. Each request is capped at one provider call, zero retries, 30 seconds, and bounded output tokens (2,500 for full specs; 700 for patches). Validation and provider failures return errors; Live never falls back to Offline. Provider metadata exposes model, latency, request count and available token usage, but no key or raw prompt. Cost is returned as `cost_usd=null`, `cost_status=unavailable` until a verified price source exists. No live inference was executed for this task.

The JSON route has an upstream 100 kB body cap. Source lookup is repository-scoped, bounded by indexed files and file size, and skips lines resembling credentials. Public production continues to return 503. Account-wide paid request accounting and rate limiting are **not implemented for this new route**; the development-only/owner-only gate must remain until those controls and a security review exist. The existing analysis route has its own entitlement path; V2 does not weaken it.

## Impact analysis boundary and limitations

The workspace passes the original requirement, explicit refinement, selected source reference (when grounded) and validated patch tokens to the existing text or screenshot analysis endpoint. `AnalysisOrchestrator`, `EvidenceValidator` and `CausalImpactVerifier` remain responsible for source-grounded direct/indirect/potential findings. The preview tree is never evidence of a repository edit. A conceptual target yields no claimed source file in the proposal response. A style-only impact report still needs human review of causal scope; this feature does not prove that every existing analysis result is narrowly scoped. The static target resolver cannot reconstruct complete TSX runtime state, dynamic labels, CSS cascade or actual click behavior. Exact existing-screen before/after requires a captured baseline or a future safe source renderer.
