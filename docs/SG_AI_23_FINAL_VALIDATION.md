## Confirmed integration defects fixed

1. The screenshot API could return HTTP 200 with `status="failed"` when the vision provider was unavailable. The web client previously treated this as a successful fetch and `RepoContext` silently dropped the run. It now raises a distinct failure, clears stale report state and shows a localized alert. The offline backend's status contract was preserved.
2. The report called untrusted visual output “grounding” and gave no clear boundary between image observations and source-backed impact claims. The visual section now says **Visual observations (unverified)**, displays model uncertainty and explains that code impacts below require source evidence. The backend continues to omit OCR text and detailed visible elements from persisted reports for privacy.
3. The browser accepted `image/jpg` although the API accepts `image/jpeg`, and accepted up to 5 MiB while the API limit is 5,000,000 bytes. The attachment control now uses the exact API MIME list and byte limit. Browser checks observed both mismatches before the fix and rejection after it.

Pre-existing GitHub OAuth and progress-document edits in the working tree were preserved.

## Security and compatibility review

- **Repository authorization:** `analysis.py` looks up repository ID and readiness but has no session, owner or access dependency. Report/status routes similarly query by analysis ID without an ownership check. An unauthenticated GET of `/api/v1/repositories` returned HTTP 200 during this review. Private repository ingestion must not be publicly exposed under this access model.
- **Multipart request size:** The route reads only `MAX_SCREENSHOT_BYTES + 1` from the already parsed `UploadFile` and rejects excess with 413. Starlette parses/spools the multipart body before entering the route. No upstream body limit or request-size middleware was found in the local app/Vite configuration. The per-image check therefore does not bound total incoming multipart bytes or pre-route parsing work.
- **Runtime provider settings:** `GET /api/v1/system/info`, `PUT /api/v1/system/settings`, and `POST /api/v1/system/test-ai` have no authorization dependency. An unauthenticated GET of `system/info` returned HTTP 200. The response schema includes `custom_api_key`; its value was empty in this check, but the implementation returns a user-supplied runtime key verbatim when present. The update route accepts provider, model, key and arbitrary base URL; the test route can trigger inference. Do not expose these routes publicly without authentication, authorization, destination validation and request/spend controls.
- **Stored visual metadata:** The report stores bounded screen type and uncertainties. They are untrusted model observations and may still reveal UI information. Retention and access policies are unresolved.
- **Compatibility:** The text-only endpoint, JSON request shape and no-image result shape remained unchanged in regression tests. The screenshot route stays synchronous and bypasses the text cache. The mocked vision response validates transport, schema, retrieval and UI presentation; it does not measure Meta vision accuracy or end-to-end live-model quality.
